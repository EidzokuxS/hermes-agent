# План основания Nox

> Статус: исследовательский predecessor. Единственным execution source является [`docs/goals/nox-first-causal-loop/PLAN.md`](../../../docs/goals/nox-first-causal-loop/PLAN.md). Этот документ сохраняет раннее архитектурное обоснование и не служит очередью исполнения.

## Архитектурная ставка

Nox развивается как собственный TypeScript-проект. Pi подключается закреплённой зависимостью на уровне AI и agent core. Hermes Desktop переносится как донорский snapshot с сохранением лицензии, провенанса и исходного frontend-стиля. Собственный runtime и протокол событий образуют центр системы.

## Первая точка успеха

Первой точкой успеха считается один доказанный причинный цикл Nox, показанный в Desktop GUI и переживший остановку процесса.

Сценарий:

```text
State S0
  -> Event E1 из GUI
  -> Act A1 через Pi-кортекс
  -> принятые Effect
  -> State S1 + emission или тишина + возможный Continuation C1
  -> полная остановка runtime
  -> восстановление State S1 из устойчивого хранилища
  -> Event E2 из C1 либо новый Event Эйдзи
  -> Act A2 с доступом к S1 и прошедшему времени
```

В Journal должна восстанавливаться цепочка `E1 -> A1 -> Effect -> S1 -> E2 -> A2`. Второй Act получает собранное состояние, а не весь transcript как суррогат идентичности.

## Критерии прохождения

1. GUI записывает сообщение Эйдзи как Event и подтверждает его доставку до запуска кортекса.
2. Runtime детерминированно собирает вход и сохраняет его hash, версии State и сборщика.
3. Кортекс возвращает типизированное предложение; runtime валидирует и атомарно применяет допустимые Effect.
4. Завершённый Act различает emission, осмысленную тишину, отмену и ошибку.
5. Жёсткий перезапуск восстанавливает State, временной якорь и открытые Continuation.
6. Continuation способен породить Event после перезапуска; детерминированный тестовый кортекс доказывает этот путь независимо от вариативности реальной модели.
7. Реальный кортекс выполняет ту же вертикаль хотя бы с внешним вторым Event; его выбор emission или тишины остаётся свободной переменной.
8. Полный causal trace объясняет происхождение каждого изменения State и каждого отображённого результата.
9. UI показывает версию State, состояние текущего Act и наличие ожидающих Continuation настолько, чтобы тишина и сбой визуально различались.

## Признаки провала основания

- Сообщение автоматически превращается в обязательную задачу с критерием выполнения.
- История чата становится единственным носителем идентичности и состояния.
- Перезапуск создаёт новую причинную линию либо теряет открытое продолжение.
- Сырой вывод модели меняет устойчивое состояние в обход типизированного Effect.
- Таймер или scheduler генерирует занятость и давление вместо исполнения конкретного Continuation.
- Фильтр может удалить свидетельство о собственном отклонении из независимого Journal.
- GUI отображает отсутствие текста одинаково для тишины, ошибки и зависания.

## Последовательность работы

### Фаза 0. Основание репозитория

- Инициализировать Git-репозиторий Nox в текущем workspace и зафиксировать исходные концептуальные документы.
- Закрепить точные ревизии Pi и Hermes Desktop и сохранить лицензионный провенанс.
- Создать TypeScript monorepo Nox с `apps/desktop` и собственными пакетами протокола, runtime и адаптеров.
- Создать корневой и scoped `AGENTS.md`: Nox-канон, upstream-стиль, команды, границы модулей и проверки.
- Зафиксировать зелёный baseline донорского GUI и минимального вызова Pi до смысловых изменений.

Условие выхода: проект воспроизводимо устанавливается, собирается и запускает неизменённые донорские поверхности.

### Фаза 1. Протокол причинности

- Описать TypeScript-типы и runtime-схемы для Event, State, Act, Effect, Continuation и Journal.
- Зафиксировать причинные ссылки, провенанс, версии и статусы завершения.
- Создать golden fixtures и проверки запрещённых переходов.

Условие выхода: схемы выражают все инварианты первой вертикали и отклоняют переход State в обход Effect.

### Фаза 2. Headless runtime

- Реализовать Journal, снимок State и детерминированный reducer.
- Реализовать сборщик входа кортекса и hash его состава.
- Подключить fake clock, fake cortex и in-process interface.
- Провести сценарий `E1 -> A1 -> C1 -> restart -> E2 -> A2` без сети и GUI.

Условие выхода: автоматический тест после перезапуска воспроизводит тот же State и причинную цепочку.

### Фаза 3. Pi-кортекс

- Реализовать `CortexPort` поверх низких слоёв Pi.
- Определить один структурированный контракт предложения Act.
- Добавить отмену, лимиты одного акта и типизированные ошибки провайдера.
- Сохранить полный вход и операционный выход для воспроизводимого аудита без сохранения скрытого chain-of-thought.

Условие выхода: реальная модель совершает Act, а runtime сохраняет исключительное право применять Effect.

### Фаза 4. Hermes-derived Desktop

- Перенести минимально необходимую поверхность Hermes Desktop и сохранить её frontend-конвенции.
- Заменить Hermes gateway client на `InterfacePort` протокола Nox.
- Представить Event, emission, тишину, состояние Act, версию State и Continuation.
- Сохранить streaming, interrupt и steering там, где они соответствуют контракту Nox.

Условие выхода: вся первая вертикаль проходит через Desktop без отдельного CLI-сценария.

### Фаза 5. Приёмка первого рубежа

- Запустить детерминированный интеграционный сценарий с fake cortex.
- Запустить сценарий с реальной моделью и двумя разнесёнными во времени Event.
- Остановить процессы между актами и подтвердить восстановление.
- Сопоставить State, Journal, hash входов и наблюдаемое состояние GUI.
- Провести негативные проверки из раздела о провале основания.

Условие выхода: выполнены все критерии первой точки успеха, а журнал позволяет независимо восстановить причинную историю.

## Порядок следующих исследований

После первого рубежа последовательность определяет наблюдаемый дефицит системы. Базовый порядок: метапамять и извлечение, политика внимания, инструменты и юрисдикция, более богатые продолжения, мультимодальность, характер и ратификация, специализированный кортекс.
